# Architecture decisions

## Modular resource references

Four modules expose explicit outputs rather than discovering resources by mutable Name tags. The two availability zones are configurable and must belong to the selected region. Terraform tracks dependency ordering through references.

## Cost-aware compute and database

Two `t3.micro` web instances provide placement across two zones, with CPU target tracking and a maximum of three. One `db.t3.micro` RDS MySQL 8.4 instance uses encrypted 20 GiB gp3 storage. MySQL 8.4 avoids the older MySQL 8.0 baseline. Engine/class availability must be confirmed in a real regional plan/deployment. The database is Single-AZ by default: subnet coverage alone does not provide database HA. `db_multi_az=true` increases resilience and cost.

The source project uses two Aurora `db.r5.large` instances and NAT gateways. This lab replaces those choices explicitly rather than implying equal production availability.

## Network boundaries

Web instances reside in public subnets with outbound Internet access but no SSH rule or direct public web rule. SSM provides administration. The ALB may reach port 8080; only web security-group members may reach the database on 3306. Database subnets have no Internet route. Web egress is limited to HTTP/HTTPS and MySQL to the database group. HTTP egress is retained for distribution package repositories. AWS-provided VPC DNS is handled by the VPC resolver.

CloudFront's managed prefix list has security-group rule weight 55. Only the active origin listener port is admitted, avoiding two prefix-list rules exceeding the typical 60-rule quota. A private origin header prevents other CloudFront distributions from trivially using this ALB. The token is generated by Terraform and stored in state; restrict access to state and plans.

## Transport security and domain ownership

Browser to CloudFront uses HTTPS and the default CloudFront certificate without needing a purchased domain. RDS requires TLS, and the application validates the RDS CA chain and hostname.

The no-domain lab uses HTTP from CloudFront to ALB and ALB to EC2. This is a documented lab compromise: the origin token travels over HTTP, and security groups are not encryption. For sensitive workloads, supply an existing domain, regional ALB ACM certificate and matching origin DNS name to enable CloudFront-to-ALB HTTPS. Custom viewer DNS uses an ACM certificate in us-east-1. Certificates are supplied rather than requesting a domain or inventing ownership. ALB-to-EC2 TLS, private application subnets, VPC endpoints and private origins remain production hardening work.

## Credentials and identity

RDS generates its master password in Secrets Manager. It is neither a Terraform input nor application source. EC2 reads only that specific secret through its IAM role and requires IMDSv2. The example uses the RDS administrative database identity solely for a read-only `SELECT 1` lab probe; a real application should use a separately provisioned least-privilege database user. Secret retrieval on each probe handles password rotation at the expense of API cost/latency.

The application returns sanitized database failures without exception details. The systemd process runs as an unprivileged user, with a read-only system and automatic restart. Python's standard HTTP server is suitable for this small lab, not a production high-throughput application server.

## Health and observability

ALB liveness checks use `/health`, so a database outage does not cause all healthy web instances to be replaced. `/db` independently verifies the data tier. WAF publishes CloudWatch metrics and sampled requests; RDS exports error/slow-query logs; systemd logs are available through SSM. Full centralized application/access logs, alert delivery and load-tested autoscaling are not implemented or claimed.

## Lifecycle

The lab uses local Terraform state and no automatic apply in CI. For shared production use, migrate to an encrypted, versioned S3 backend with native S3 locking and scoped IAM. Database deletion protection and final snapshots are configurable. Default teardown deliberately removes disposable lab data. CloudFront deletion can take time; retain state and wait for completion.
